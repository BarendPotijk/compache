compacheCalculator

How the calculator works

The calculator prices one chat workload twice from token counts and list prices: once with a Compache policy fitted to that workload, and once with OpenClaw's documented defaults. It runs in the browser from site/, with no dependencies, keys, telemetry or provider requests.

It is a model. No model is called, neither product is executed and answer quality is not measured. The Compache side is a simplified projection of the package's policy. The DocChat benchmark runs the package itself.

Run it

python3 -m http.server 8765 --bind 127.0.0.1 --directory site   # then open http://127.0.0.1:8765/
node --test site/*.test.mjs
  • Share copies a link that carries every setting. Links made by earlier versions still open, with a note that their numbers were computed differently.
  • Export downloads the settings, the sampled threads, every priced call, every candidate policy and the limits below.
  • Import reads a profile made from your traces or a file exported here. You can also drop the file on the page.
  • A setting that is unknown or out of range is reported on the page. Nothing falls back to a default unnoticed.

Workload

  • Two sets of threads. One seed draws the threads the policy is fitted on. The next seed draws the threads both sides are costed on. 100 threads each by default.
  • Thread length is lognormal (median and 95th percentile), fixed, or geometric (mean), capped at 160 turns. Before every further turn the thread continues with a set chance.
  • By chance of another turn is a fourth way to set the length, for traffic with many one-turn threads and long threads that keep going. The chance moves from its value after the first turn to its value in long threads, and is halfway after a set number of turns.
  • Each turn adds a question, retrieved text and an answer. Retrieved tokens are lognormal. A set share of turns retrieves, and the others add a question and an answer only. Zero retrieved tokens means no retrieval at all. The system prompt and tools start every request.
  • Return delay is lognormal. Its median and 95th percentile describe long threads. After the first turn the delay is a set multiple of that, and it moves to the long-thread value as the thread goes on. A set share of returns are long breaks instead, whatever the turn: lognormal around their own median, with a 95th percentile four times that. A user who does not return is a thread that ended, not a long delay.
  • Answer time. The next question arrives one answer time plus the return delay after the request was sent.
  • What later turns need. For questions, retrieved text and answers separately, a turn needs one earlier item of that kind with a set chance. How far back it lies is lognormal with a median and a 95th percentile, rounded to a whole turn, at least one, and limited to the turns that exist. A 95th percentile equal to the median means exactly that many turns back. Retrieved text can only be needed from a turn that retrieved: the distances are weighted over those turns, and before any turn has retrieved there is no such need.

After turn n of a thread, with h the turns to halfway of each effect:

chance of another turn = long - (long - first) × 0.5^((n - 1) / h)
median return delay    = median × factor^(0.5^((n - 1) / h))

Prices and cache

Every request is a sequence of blocks with fixed identities and sizes. For each call, with rates per million tokens:

fresh = input - cached
cost  = fresh  × input_rate × cache_write × long_input  / 1,000,000
      + cached × cache_read_rate          × long_input  / 1,000,000
      + output × output_rate              × long_output / 1,000,000
  • Cached is the longest start a request shares with an earlier request of the same thread that has not expired, in whole cache blocks and at least the model's minimum. An entry lives exactly the configured lifetime from when the request that wrote or read it was sent.
  • A shared system prompt. A request that finds less of its own thread cached than the system block reads that block with a set chance: another conversation with the same prompt has cached it. The block must reach the cache minimum. The chance is 0 by default, and OpenClaw's flush and summary prompts are never shared.
  • A live entry is read for a set share, all of it by default. This and the shared prompt are priced at the expected tokens read. No outcome is drawn.
  • Further calls. A turn that makes more than one model call sends its request again for each further call, with no output: read from the cache where the request can be cached, at the plain input price otherwise. Both sides pay it.
  • Reasoning is billed as output with each answer and is not sent again.
  • A request below the cache minimum pays the plain input price for its fresh tokens.
  • The long-request rates apply to the whole request once its input exceeds the threshold. Zero turns them off.
  • An answer enters the cache only when a later request carries it.

The Compache side

Questions and answers always stay in the request. Only old retrieved text is archived, and each turn's archived text leaves a notice in its place (22 tokens by default, what the package leaves for one part). A policy is three numbers:

NumberMeaningCandidates
Compact toAt a cold return, a request more than two points above this share of the window is compacted down to it, oldest retrieved text first1%, 3%, 5%, 10%, 20%, 45%
Warm atWhile the cache is warm, compaction waits until the request reaches this share of the window5%, 10%, 25%, 50%, 60%
Keep turnsRetrieved text from the latest turns is never archivedNone, or enough turns to cover 25%, 50%, 75%, 90%, 95% or 99% of the retrieved text later turns need
  • With the default workload that is 147 candidates: 21 pairs of the first two numbers, each with seven horizons. A run in which the warm trigger never decided anything is shared by every higher trigger, which changes no result.
  • The floor. A candidate must finish every turn and leave at least the chosen share of what later turns need in the request, before anything is fetched back. That share is an expectation over the configured chances and distances, taken on the fitted threads. With no needs at all there is no constraint.
  • The choice. The cheapest candidate on the fitted threads wins. Among equally cheap ones, the one that removes least. Both sides are then costed on the second set of threads.
  • Fetching back. A turn that needs an archived source pays one extra call that reads the request and returns a short reply (32 tokens by default). The answer call then carries the source again.
  • Admission. A request must fit the model's input limit and leave the reserve free (32,000 tokens by default). A thread that does not fit is reported, and no saving is shown.

Keep-warm pings. After each answer the planner weighs, for one to twelve pings, the chance that the user returns in the extra time the pings buy times the cost a warm return avoids, against every ping sent while waiting. It uses the configured chance of another turn and return delay at that turn's position, never the sampled future. Pings go out a set lead before the cache would expire and stop when the user returns. They are charged when the user never does. No ping is sent for a request that the next warm turn would compact anyway, for one too short to cache, or when the answer is still running as the first ping falls due.

With F the share of returning users back within a delay at that position, d the answer time and the interval one lifetime less the lead, both counted from when the request was sent:

back before ping n   = F(n × interval - d)
bridged by n pings   = F(n × interval + lifetime - d) - F(lifetime - d)

What that keeps and costs is not published in a form this page can price, so the client-side summary stands in for it. Whether a summary still carries a fact is not evaluated: a summarized source counts as no longer in view.

Reading the page

  • Cost per 1,000 turns is the cost of every answer, further call, ping, fetch-back, summary and flush call on the costed threads, divided by their turns.
  • Needed sources in view is, of everything turns needed, the share that was in the request before anything was fetched back.
  • Input read from cache counts the input tokens of answer calls only.
  • Tokens per turn averages the request size over the threads that reach each turn on both sides. The bars below it show how many that is.
  • Keep-warm pings shows the planner's amounts after one turn, per 1,000 waits. In the average view it averages the same plan over the threads that can be pinged at that turn.
  • Input tokens of answers splits answer input into what was read from the cache and why the rest was not: new this turn, the first turn of a thread, an expired entry, a request that changed before that point, or a live entry that was not read.

Limits

  • Token counts and list prices are assumptions. A cache entry is taken to live exactly its configured lifetime. Providers may keep it longer or evict it sooner.
  • A turn's further calls repeat its first request. Text that a tool loop adds between calls counts as arriving with the question. Answer time is one number for every turn.
  • The chance of another turn and the return delay depend on a turn's position. What a turn retrieves and what it needs do not.
  • Both sides know which earlier sources a turn needs. Real requests have to find that out.
  • Needs are independent draws per kind. A real thread has structure this does not capture.
  • The policy is the cheapest of a finite set of candidates, not the package's fitted policy. It removes whole retrieved blocks.
  • Pings can raise the realized cost: the planner decides on expectations.
  • OpenClaw's summary quality, retries, memory tools and its OpenAI compaction path are not modeled.
